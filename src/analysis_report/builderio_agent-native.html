GitHub: https://github.com/builderio/agent-native

一句话总结

Builder.io agent-native 是一个 TypeScript 应用框架，把「一次业务操作」同时定义为 React hook、agent tool、HTTP endpoint、MCP tool、A2A skill 和 CLI 命令——让 AI agent 与人共用同一份 SQL 数据、同一份应用状态、同一段执行路径，agent 不再是外挂聊天框，而是 product 的第一公民。

值得关注的理由

  • 稀缺定位：在「CopilotKit 是给现有 React 应用塞聊天面板、LangGraph 是 agent 编排库、Flowise 是 ops 工作台」的红海里，agent-native 是 2026 年少数把「agent + UI 共享 action / data / state」做成生产级框架的开源项目。
  • 公司级战略投入：Builder.io 是成立 13 年的 Visual CMS 老牌公司（YC W15），CEO Steve Sewell 亲自贡献 50.4% commit，6 个月 5,856 commits、月峰值 1,258 commits、单仓 3.6M 行代码、23 packages + 19 完整 SaaS 模板 + 12 skills，密集开发期仍未结束。
  • 深度工程化：1,090 个 spec 文件、30+ diff-scoped guards、AGENTS.md + 24+ SKILL.md 的两层 governance、ActionContractError + fail() 单一错误语义穿 6 transport、SyncTransport 单例 + Web Lock leader/follower 跨 tab SSE 共享——每一项都是可以单独拎出来读的工程实践。

作者视角：为什么存在这个项目

创始人/作者背景

仓库归属 Builder.io（Organization），账号年龄 8.7 年，93 个公开仓库，3,068 粉丝。Steve Sewell（GitHub: steve8708）作为 Builder.io 创始人兼 CEO，是仓库绝对主笔——首提交即为整仓一次性导入、6 个月 5,856 commits 中本人独占约 50.4%。Builder.io 长期在「让非工程师编辑 React 组件 / 可视化拖拽结构化内容」这条线上，2013 年成立、YC W15 出身。agent-native 是其把视觉化能力延伸到「让 AI agent 与 UI 共享同一执行层」的旗舰开源项目，CEO 亲自下场本身就是「公司级战略」的强信号。

问题判断

当下 AI agent 与 UI 是两条平行轨道：agent 用 tool call + JSON-RPC，UI 用组件 + HTTP，业务能力定义双份、权限/审计各写一套，结果就是「Demo 级 agent 写得很快，生产级产品推不上去」。Builder.io 看到的裂缝具体是三件事——

  • 能力定义双份：UI 函数和 agent tool 各写一套，权限 / 审计 / 治理漂移；
  • 数据视图分裂：agent 改完数据库，前端不会立刻看到；多 tab / 多进程 cold-start 拿不到「刚才那条写入」；
  • 状态机不共享：LLM 不知道你停在发票列表第 3 行、不知道你刚才选了哪条记录。

独立观察（mer.vin）把这条裂缝概括得很准：现有方案要么是「chat 后端 + REST 后端」双层（CopilotKit/AG-UI），要么是「拖拽工作台」不交付产品（Flowise/Sim），要么是「agent 编排库」不管 UI 集成（LangGraph/AutoGen）。Builder.io 自己的 Visual Copilot 是「设计 → 代码」辅助工具，也不解决「生产级 agent 应用」这一层抽象。

解法哲学

agent-native 把上面这条裂缝具体化成「Shared Actions / Shared Data / Shared State」三个共享层：

  • Shared Actions：一个 defineAction({ description, schema, http?, run, authorize? }) 是唯一入口，自动以 React hook、agent tool、HTTP endpoint、MCP tool、A2A skill、CLI runner 六种方式暴露；ActionRunContext.caller 区分 8 种调用来源，权限与审计只过一处；
  • Shared Data：所有 app state、agent run state、chat thread、tool approval、resources、application_state 都落 PostgreSQL（Drizzle），通过 SSE 推到 React Query，250ms 合并窗口防抖，fallback poll；
  • Shared State：(session_id, key) 主键的 KV 表 + x-agent-native-browser-tab per-tab scope，UI 主动 push、agent loop 主动读，cursor / selection / 活动视图都进 prompt context。

AGENTS.md 的关键信条：「the agent should never click through the UI, both call the same action layer」——这是与「聊天框外挂」流派最根本的分歧。

战略意图

这是 Builder.io 公司从「Visual Copilot for code」到「Visual Copilot for product」的战略升级：

  • 核心产品位置：旗舰开源项目，不是社区实验；
  • 商业化路径：packages/dispatch（vault / integrations / scheduled jobs / cross-app delegation）、packages/migrate（迁移 Workbench）、packages/pinpoint（视觉反馈标注）——三个包都是「之前 SaaS 沉淀的可单独商业化」的控制面入站仓；
  • 开源策略：genuinely open-core，runtime + 9 templates + 12 skills + 24+ SKILL.md 全部 ISC license 开源，商业化点放在控制面而非 runtime。

仓库内 AGENTS.md + PRODUCT.md + 9 个内置 app + 12 个 .agents/skills/* 构成完整的「自描述框架」，没有外部博客/架构长文，但仓库本身就是最好的架构文档。

核心价值提炼

创新之处

按新颖度 × 实用性排序：

  1. Shared Actions（一个 Zod schema 驱动 6 个 surface） — 新颖度 4/5 · 实用性 5/5 · 可迁移性 4/5。CopilotKit AG-UI 协议只覆盖前两层（UI + agent tool），MCP 协议解决 tool-call 暴露但不解决和 app 本身 action 层的关系；唯一同时覆盖到 A2A + MCP + 应用原语 action 的开源实现，截至 2026/9 罕见。
  2. Agent-native CRDT cursor/selection ring 暴露给 agent 当 context — 新颖度 5/5 · 实用性 3/5 · 可迁移性 3/5。把 CRDT 思想反向出口给机器用户（独立评论明确点出这是「CRDT for agent+UI merge」），2026 年前没有成熟先例。
  3. SyncTransport 单例 + Web Lock leader/follower + BroadcastChannel 跨 tab SSE 共享 — 新颖度 4/5 · 实用性 5/5 · 可迁移性 5/5。Google Docs / Figma / Linear 都做过「多 tab 单连接」但都是闭源 + 自家 infra；前端框架层面把这个模式开源出来的，截至 2026/9 罕见。
  4. runAgentLoop 用 per-turn input token 累计预算代替 iteration budget — 新颖度 4/5 · 实用性 5/5 · 可迁移性 5/5。注释里直接写「Iteration count and wall clock do not bound spend — retained tool results are re-sent every iteration, so cost is quadratic in tool-call count」。LangGraph 文档明确讨论过 cost-vs-iteration 但没有 per-turn cap 抽象。
  5. ActionContractError + fail() 单一契约错误跨 6 transport — 新颖度 3/5 · 实用性 5/5 · 可迁移性 5/5。鸭子类型 actionContractError === true 让契约在序列化中幸存；非契约错误归一为 500、契约错误保留原 message + code；CLI / agent tool / HTTPS / A2A / MCP 看到同一语义。
  6. fireInternalDispatch 自递归 HTTP + HMAC — 新颖度 4/5 · 实用性 4/5 · 可迁移性 3/5。写 SQL run row → HMAC 签 → POST 回自己 deployment → 250ms race-timer 防 serverless「return 早于 dispatch 出栈」；serverless-first SaaS 的通用后台任务模式。
  7. 30+ diff-scoped guards + 三元退出码 + agent-friction-report — 新颖度 4/5 · 实用性 4/5 · 可迁移性 3/5。CI 自动跑 30+ 个 diff-scoped guards（guard:no-action-twin-routes、guard:ssr-cache-shell、guard:i18n-catalogs、guard:hooks-registered），guard 退出码三元（0 pass / 1 fail / 2 could-not-run），CI 守住「不可能误判为 pass」。

可复用的模式与技巧

  1. Schema-first Multi-surface Action：以 Zod schema 为单一来源，runtime 自动 expose 到 UI / agent / HTTP / MCP / A2A / CLI，caller 标签让 cross-cutting 治理只在一处实现。适用场景：任何「agent + UI 共用同一份业务原语」的 SaaS。
  2. Module-level SyncTransport + Web Lock Leader/BroadcastChannel Follower：一份 SSE 连接供应 N 个 tab、多个 hook、N 个 query client 的「leader/follower」模式，靠 Web Lock 自然 failover。适用场景：tab-heavy 后台、邮件、看板、表单工具。
  3. Per-turn input-token budget 替代 iteration budget：把 LLM loop 截断门从「次数」换成「累积 input token」，对 chunked turn 做 token 预算累加。适用场景：所有生产级 agent loop。
  4. Contract-typed error object 在多 transport 间幸存：鸭子类型 + 显式 fail() helper，让业务错误能在 HTTP / JSON-RPC / MCP / A2A / CLI 间稳定穿行。适用场景：所有 multi-surface SDK。
  5. Self-Dispatch over HMAC + SQL run row：serverless 后台任务的「自递归 POST 自己」通用化实现，hostvars 决定「自己」。适用场景：Netlify / Vercel / Cloudflare Workers 上的后台任务。
  6. Invariant-only Root + skill-only Detail 的两层 governance：AGENTS.md 列 invariant、.agents/skills/* 列 why，加 diff-scoped guards 自动核对。适用场景：多 IDE / 多 agent 协作的 monorepo。
  7. Application-state as ambient KV with per-tab scoping：UI 主动 push + agent 主动读 + 双向实时同步，让 agent 知道「人在哪里」。适用场景：需要「人在回路」的协作型 agent 应用。

关键设计决策

  1. 决策：Shared Actions 单一入口
    • 问题：UI 函数 vs agent tool 双写导致权限/审计漂移
    • 方案：packages/core/src/action.ts defineAction 为唯一入口，自动暴露为 React hook / agent tool / HTTP / MCP / A2A / CLI，ActionRunContext.caller 区分 8 种调用来源
    • Trade-off：付出框架绑定成本（Nitro/TS 宿主、framework schema-prompt 契约）换来治理一致性
    • 可迁移性：高
  2. 决策：SQL 为单一 SoR，SSE + 250ms 合并窗口实时同步
    • 问题：agent 后台改数据前端必须立刻看到；多 tab / 多 cold-start function 间需要统一拿到「刚才那条写入」
    • 方案：所有 state 落 PostgreSQL（Drizzle），客户端通过 useDbSync 订阅 /_agent-native/events SSE，notifyActionChange + writeActionChangeMarker + publishActionChangeFastPath 推 version 单调递增事件，250ms 窗口合并防抖动；fallback /_agent-native/poll
    • Trade-off：SSE 长连接消耗浏览器单 origin ~6 连接配额；UI 选型必须用 React Query；状态层必须能被 Drizzle 表达
    • 可迁移性：高
  3. 决策：runAgentLoop 按 turn 增量控制 max-run-input-tokens
    • 问题：传统 maxIterations 截断让成本不可预测（retain tool result 重发 → quadratic cost）
    • 方案：priorTurnInputTokens 防 chunked turn 刷新预算；MAX_TURN_WALL_CLOCK_MS 同时作为壁钟硬上限
    • Trade-off：按 token 截断更难预测「跑了几步」，需要模型支持或准确的 tokenization
    • 可迁移性：高

差异化护城河

  • 技术护城河：Shared Actions（Zod schema → 6 surface）是 2026 年开源领域独此一家的端到端抽象；Web Lock + SSE leader/follower 解决 6-origin 浏览器真痛点；per-turn input-token 预算是 agent 框架里稀缺的「成本可控」抽象。
  • 生态护城河：9 个内置完整 SaaS 模板、12 个 skills、24+ AGENTS.md skills、30+ pnpm guards，是其他框架无可比拟的「能直接开跑」的 demo 库存——其他 agent 框架给的是 SDK，agent-native 给的是完整产品。
  • 信任护城河：Builder.io 13 年 SaaS 经验、CEO 50% commit 量、ISC 全开源、3.6M LoC monorepo 已写完并跑在 production（beta、docs、客户托管），不是「PPT 框架」。

竞争风险

  • 最大风险：「低门槛集成派」CopilotKit AG-UI 一旦把「shared action」抽象化、推出标准化协议，开发者无需重写整个应用即可获得 80% 的能力；以及「agent ops 派」LangGraph / CrewAI / Sim 把 agent 编排 UX 做透后，吸引创业者把 agent-native 当「应用层」、把 LangGraph studio 当「调试层」使用。
  • 次级风险：6 个月 5,856 commits 但 Refactor 0% / Fix 52%——项目早期「先建后清」是合理的，但 0.7.x 阶段的技术债一旦爆发，会显著拖累商业化进度。

生态定位

「AI-era 应用框架」——既不是 chat layer、不是 agent runtime、不是 ops 工具，而是「SQL 持久 + React UI + shared action + agent loop + 多 surface 暴露」一体的产品化运行时；类似 Rails / Next.js 在 AI 时代的对应位置。

套利机会分析

  • 信息差：项目被低估——名字「agent-native」在通用 AI agent 红海里被淹没（LangChain / AutoGen / CrewAI / LangGraph 占用心智），但它实际是 2026 年少数把「UI 与 agent 共享 action / data / state」做成生产级框架的项目，6K stars 体量与定位不匹配。
  • 技术借鉴：SyncTransport 单例 + Web Lock leader/follower、runAgentLoop per-turn input-token 预算、ActionContractError + fail() 三项是「读懂即可 1:1 抄到自己项目」的工程实践，与框架无关。
  • 生态位：填补了「agent 框架 + 应用框架」之间的空白层——LangGraph 等只管 agent 不管应用，Next.js 等只管应用不管 agent，agent-native 把两者焊在一条 shared action 流水线上。
  • 趋势判断：项目仍处于「密集开发期 + 月度 commit 单调递增」状态（曲线从 437 → 1,258），符合 AI 基础设施层级的增长曲线；6 个月完成 v0.7.83、按 changesets 多包独立发版（2,670 个 tag / 100 个 release），说明有清晰的 release 节奏和对外 API 稳定性承诺。

风险与不足

  • 6 个月、5,856 commits、Refactor 0% / Fix 52%：反常的 commit 类型分布——不是项目不成熟，而是「产品 + 模板 + skills 同时铺开、bot 自动 squash 合入保留 PR 原标题」的副作用。0.7.x 阶段开始，技术债会显性化。
  • 强约束宿主：必须 PostgreSQL + Nitro + TypeScript；不是 Next.js drop-in；不支持 JVM/Kotlin/Spring（独立评论明确指出 4 条「不适用场景」）。这意味着它不是 retrofit 工具，是 greenfield 框架——选型时不能「先选它再想怎么集成」。
  • 6K stars 仍属「被低估」状态：star 体量与定位错配，社区认知度还需 6-12 个月才会追上来；商业化断面（hosting / migration / cross-app orchestration）尚未明确披露 SaaS 定价。
  • CEO 单点风险：50.4% commit 集中在 Steve Sewell 一人，company-strategic OSS 的典型风险，公司战略调整会直接影响项目。
  • issues 噪声：当前 17 个 open issues 几乎全是 CI 健康检查 noise（自动开闭），实际用户 issue 几乎不可见，社区反馈循环不清晰。

行动建议

  • 如果你要用它：
    • 适用场景：greenfield 启动一个「agent 是产品一等公民」的 SaaS，且团队接受 PostgreSQL + Nitro + TypeScript 全栈锁定；
    • 不适用场景：给现有 React/Next.js 应用加 chat、纯 agent 编排层、不愿锁定 PostgreSQL 宿主的团队；
    • 对比 CopilotKit：选 CopilotKit 如果「给现有应用加 chat」是核心需求；选 agent-native 如果「agent 改应用代码、改 SQL、改 UI」是核心需求。
  • 如果你要学它：
    • 重点关注 packages/core/src/action.ts（defineAction 核心）、packages/core/src/agent/production-agent.ts（核心循环，12k+ 行，含 per-turn budget 注释）、packages/core/src/server/agent-chat-plugin.ts（服务端 SSE/stream）、packages/core/src/client/use-db-sync.ts（SyncTransport 单例 + Web Lock leader/follower）；
    • 必读文档：AGENTS.md（invariant）+ PRODUCT.md（设计哲学）+ .agents/skills/*（24+ SKILL.md，覆盖「why」）。
  • 如果你要 fork 它：
    • 改进方向：替代 Drizzle 为 Prisma（如果团队习惯）、简化 production-agent.ts 12k+ 行的单文件结构、增加 Next.js adapter（目前 Nitro 绑定）、补充可视化调试工具（agent timeline 类似 Sim 的能力）。
